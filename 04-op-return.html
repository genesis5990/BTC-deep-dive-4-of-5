OP_RETURN: Data Riding the Rails

Remember T2 in the lab — it had an output worth 0 BTC that wasn't change and wasn't a payment. That's the signature of OP_RETURN.

What it is

OP_RETURN is an opcode that makes an output provably unspendable, forever. Anything locked with OP_RETURN can never be spent — nodes can even prune it from their UTXO set. Consensus allows up to 80 bytes of arbitrary data to be pushed after it.

It exists precisely so people can embed small amounts of data on-chain without bloating the UTXO set with unspendable "dust" outputs. An OP_RETURN output carries information, not money — almost always sent with value 0.

What people use it for (and what that means for you)

Legitimate useTypical payloadInvestigative value
Proof of existence / timestampingHash of a document or fileAnchor proves a file existed at block time — useful for document-dating disputes; correlating the embedded hash with seized files can be powerful

Worked example — decode it by hand (2 min exercise)

The lab's T2 OP_RETURN payload (sample data):

hex: 52414e534f4d2d4e4f54453a2064697274792d3838
R A N S O M - N O T E :  ␣ d i r t y - 8 8

Every pair of hex digits = one ASCII character. Even with no tools: 52=R, 41=A, 4e=N… decodes to "RANSOM-NOTE: dirty-88" — a tag linking this transaction to the note the hospital received. That single unspendable output now ties the on-chain hop to the offender's own message.

Quick decoder for class: open any hex-to-ASCII converter offline, or use python3 -c "print(bytes.fromhex('52414e534f4d2d4e4f54453a2064697274792d3838').decode())". No internet needed. There is a decode-practice grid on the printable worksheet.

Field guide: OP_RETURN in your casework

  1. Spot it: output with value 0 and script type shown as OP_RETURN/NULldata in explorers. It never moves funds — never count it in your value-traced total.
  2. Decode it: copy the payload hex exactly; convert to ASCII; if binary, look for known protocol markers. Photograph/screenshot the raw script in your preservation, and hash the export (page 5).
  3. Correlate it: strings may match ransom notes, filenames, wallet labels, or known protocol tags. A match can be your strongest linkage evidence even when the money path is obscured.
  4. Respect the limits: 80 bytes max per output — larger messages are split across multiple OP_RETURNs (often in consecutive transactions or chained outputs). If you see PART 1/3, keep pulling the thread.
  5. Don't overclaim: anyone can write anything. An OP_RETURN "message from the suspect" proves whoever signed that transaction wrote it — tie it back to key control before attributing it to a person.
Anti-patterns to avoid: OP_RETURN outputs are not a hiding place for value (nothing can ever be spent from them) and not proof that data was "encrypted" (most payloads are plaintext or trivially encoded). Also note: some miners now accept larger non-standard OP_RETURN payloads — if you see one over 80 bytes, document it as non-standard rather than impossible.
